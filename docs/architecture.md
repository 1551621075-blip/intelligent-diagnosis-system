# 架构与边界

## 1. 这是哪个工程

一个独立、原创、只使用合成场景的数字技师应用：固定业务流程 + 实际机器学习 + 可执行知识条件。它不是自由调用工具的大模型 Agent，也不依赖生成式大模型。

本仓库为本地 Demo／测试版，用于生产部署前的本地验证，不包含企业文档、原模型、真实设备数据、内部端点或原项目业绩。合成结果不能用于推断现实设备上的诊断准确率，安全支路建议不能替代持证人员检修。

## 2. 输入 → 处理 → 输出

```text
用户主诉 ── 文本分类/拒识 ──┐
                           ├─ 领域+故障ID绑定
持续遥测 ── 水位/去重/冷却 ─┘
  → 固定时间窗/数据质量检查
  → 分域 LightGBM 输出 class_id + 多类 scores
  → 知识图 class_id → attribution_id → solution_id
  → 真实信号条件的 AND/OR 三值验证
  → 可靠性/证据/安全门
  → unknown / review_required / resolved
  → 合成服务资源排序、人工确认
  → 专家反馈 → 候选训练/知识版本 → 评测审批 → 激活或回滚
```

模型接收的是数值特征，不是图的节点或边。知识中的故障ID约束入口范围，分类标签通过明确的映射连接业务归因与方案。图并不凭模型概率认定根因，必须验证当前窗口的条件。

## 3. 五阶段

| 阶段 | 代码中的标识 | 做什么 |
|---|---|---|
| 感知 | perception | 严格解析请求/主动事件，不接受非有限数值 |
| 路由 | routing | 用户入口使用字符TF-IDF + 逻辑回归；主动入口必须绑定领域和故障ID |
| 执行 | execution | 数值窗口特征、真实LightGBM、多类输出、知识条件验证 |
| 门控 | gating | 拒识、证据冲突、安全专家复核；服务资源只作合成候选 |
| 反馈待办 | feedback_pending | 保留冻结诊断，后续反馈/派单/维修状态独立入账 |

早停时不会伪造已经执行的阶段。`resolved` 的含义是“满足本合成协议诊断条件”，不是“维修已完成”。`review_required` 也不是已得到专家批准。

## 4. 两个领域、八类合成场景

- safety：`circuit_open`、`circuit_short`、`safety_sensor_invalid`、`safety_normal`。
- low_voltage：`battery_depleted`、`charging_failure`、`terminal_resistance`、`voltage_normal`。

全部标签、设备标识、服务站、波形和阈值由本工程原创生成，不是现实诊断标准。正常类意味着“这个窗口符合本协议正常形态”，不证明设备没有其他故障。

## 5. 窗口与主动触发

`fault_time_ms ± 1000ms`，至少3个唯一采样点，故障时刻两侧均有观测、靠近窗口边缘。DTC只作带噪声信号，不能直接查表当作真实机器学习。缺值不补成0；特征检查报告问题后主流程停止。

主动入口在SQLite保存设备/领域的事件水位、滚动2秒采样（额外保留左边界前驱点）和上次触发时间。按每个新增采样时刻逐点推进：至少3点、跨度不小于2秒、全部持续告警、相邻间隔不超过1秒才触发，60秒内冷却。无需采样周期整除2秒；间隔大于1秒会中断连续段。规则是本仓库的示例策略，不是原业务参数。

一批内先告警后恢复仍保留已经触发的诊断，不借用后续样本。一个大批次可以跨过多个冷却期：响应`diagnoses`返回全部结果，`trigger_count`给出数量，兼容字段`diagnosis`只指首条。对于相同的按序采样、身份、设备、领域和位置，分批方式不改变触发时刻与派生请求ID。告警触发不保证可归因，窗口缺测时仍生成`unknown`而非伪造结论。滚动窗口（含前驱）超过1000点时整批事务拒绝，不静默截断。

- `(owner,event_id)` 相同内容返回原结果，不重复创建工单。
- 相同event_id不同内容：409。
- 水位之前的事件：明确ignored，不修改已冻结诊断。
- 跨批次窗口可以在进程重启后继续；窗口内重叠时刻内容冲突拒绝。
- 不推断缺失区间的告警连续性，不把补报旧数据倒灌改写过去结论。

## 6. 训练与版本

合成设备先分train/validation/test，同设备的全部事件保持在一个分区。实际训练两个LightGBM多类模型，验证集选择有限超参数与拒识阈值，测试分区用于冻结评测；输出先验/线性基线供比较。

可靠性门包含模型分数、熵与训练数值范围。分数是LightGBM输出，不是经过严格统计校准的故障概率；数值范围OOD不能识别所有未知故障。人工反馈不允许进入冻结验证/测试设备，训练报告保留回流接收/排除数量与来源摘要。

模型制品为LightGBM文本和JSON元数据，版本由内容哈希决定，不能同版本覆盖异内容。应用注册报告必须与加载器校验后的元数据相同。激活检查两域最低宏F1示例门0.80；已有模型升级时使用同一冻结评测指纹且分域指标不能退化。回滚只允许历史通过发布门的版本，保留原因与前后版本。

注意：本地文件系统管理员可以修改程序及重造制品，本系统的哈希不是数字签名，也不是对本机管理员的防篡改边界。企业部署需独立签名制品、受保护评测任务和审批系统。

## 7. 知识版本

networkx有向图表示类别、条件/AND/OR、归因和方案。发布前结构检查涵盖引用、环、域内类别映射和运算符。三值逻辑区分：

- supported：当前条件成立。
- refuted：当前观测反驳条件。
- missing：不能取得所需观测。

对OR返回聚合根结果，不会因为一个未选分支不成立就否定另一条已成立路径。知识版本通过草稿→独立管理员批准→发布，提案人不能自审。固定合成正反例回归、全部缺测拒识、安全门不可弱化，是独立于结构合法性的发布检查。合成回归不是现实因果验证。

## 8. 持久化与身份

- SQLite的`BEGIN IMMEDIATE`保证工单幂等、主动触发、资源预留、审批动作原子提交。
- 完整请求/结果保存在内容寻址JSON制品；SQLite记录审计引用。
- 访问令牌由本地CLI新建，只返回一次，数据库只存SHA-256摘要。
- operator只能访问自己的诊断，expert/admin按本地工作台授权查看全局。
- 这是单工作台角色边界，不宣称企业多租户隔离或完整SSO。
- 网页令牌只保存在内存，不进入URL/localStorage；所有用户文本按文本渲染。

应用默认仅监听127.0.0.1。不可把开发服务直接暴露到互联网；需要TLS、反向代理、身份管理、速率限制和备份策略时，必须另行部署与验收。

## 9. 派单和反馈不是一句“闭环”

服务候选按技能、库存、容量、距离和负载计算。人工确认时重新读取当前资源，在事务内预留工位/备件；重复动作不能重复扣减。

取消：归还预留件与工位；完成：释放工位，备件按已使用保留消耗。原始派单动作响应独立冻结，关闭后重放原action_id仍返回最初结果，不再次扣减，也不将当前关闭状态冒充原操作响应。全部状态带`synthetic_`前缀，只修改本地资源，不存在真实维修预约或设备动作。

专家反馈不覆盖原诊断，区分标签确认、模型不一致和人工行动。同一事件的冲突专家标签会阻断训练导出，不自动采用最后一个人的意见。共现挖掘只产支持度/置信度/lift候选，不证明因果，也不自动改图或发布模型。

## 10. 生产接入前仍需完成

真实采样协议与单位核对、时间同步、数据授权与脱敏、设备级留出评测、模型校准、专家复核、现实知识验证、SSO/租户隔离、备份恢复、真实服务接口和现场安全验收。此仓库没有ONNX推理、外部消息中间件或云部署；不把这些算成已经完成。
